CHANGE #1: CREATED railway.toml
─────────────────────────────────────────────────────────────────────────────

WHY?
  Modern Railway configuration using docker-compose as single source of truth
  Aligns with Laravel 12 standards shared in context
  Cleaner, more maintainable approach


WHAT IT DOES:
  [build]
  dockerComposeFile = "docker-compose.yml"        ← Uses docker-compose instead
  dockerComposeService = "app"                   ← Identifies the app service

  [deploy]
  numReplicas = 1                                 ← One container
  healthcheckPath = "/"                           ← Health check URL
  healthcheckTimeout = 30                         ← Timeout
  healthcheckInterval = 10                        ← Check frequency


WHY BETTER:
  ✓ One configuration file for local + production (no drift)
  ✓ Standard approach (same as Laravel 12 template)
  ✓ Easier maintenance (change docker-compose, everything updates)
  ✓ Clear indication which service to deploy

CHANGE #2: docker-compose.yml UPDATED
─────────────────────────────────────────────────────────────────────────────

PROBLEM FIXED #1: PORT CONFIGURATION

  BEFORE:
    ports:
      - "${APP_PORT:-8000}:8000"
    
  AFTER:
    ports:
      - "${APP_PORT:-80}:80"

  WHY?
    • Dockerfile uses Apache which listens on 80 (standard HTTP)
    • Old config tried to use port 8000 (incorrect for Apache)
    • New config matches Dockerfile reality
    • Local port 80 = production port 80 (consistency)


PROBLEM FIXED #2: VOLUME MOUNT PATHS

  BEFORE:
    volumes:
      - .:/app                           ← WRONG path
      - /app/vendor
      - /app/storage

  AFTER:
    volumes:
      - .:/var/www/html                  ← CORRECT path
      - /var/www/html/vendor
      - /var/www/html/storage
      - /var/www/html/public/uploads

  WHY?
    • Dockerfile uses WORKDIR /var/www/html (line 8)
    • Old config mounted to /app (which doesn't exist in container)
    • New config reflects actual Dockerfile structure
    • Ensures volumes are used correctly


PROBLEM FIXED #3: REMOVED PHP COMMAND SERVER

  BEFORE:
    command: php -S 0.0.0.0:8000 -t public/
    
  AFTER:
    (removed - let Apache start)

  WHY?
    • Built-in PHP server is single-threaded
    • Dockerfile is optimized for Apache (multi-process)
    • Overriding with php -S negates the Dockerfile optimization
    • Apache should start automatically from Docker image
    • Now local environment = production environment

CHANGE #3: composer.json UPDATED
─────────────────────────────────────────────────────────────────────────────

PROBLEM FIXED #1: PHP VERSION MISMATCH

  BEFORE:
    "php": "^8.2"
    
  AFTER:
    "php": "^8.3"

  WHY?
    • Dockerfile specifies php:8.3-apache
    • composer.json specified ^8.2 (inconsistent)
    • Servers will validate PHP version against composer.json
    • Must match: declared version ^8.3


PROBLEM FIXED #2: MISSING ext-intl

  BEFORE:
    "require": {
      "ext-curl": "*",
      "ext-pdo": "*",
      "ext-pdo_mysql": "*",
      "ext-mbstring": "*",
      "ext-gd": "*",
      "ext-json": "*",
      "ext-openssl": "*",
      "ext-zip": "*"
    }

  AFTER:
    "require": {
      ... (same as above) ...
      "ext-intl": "*"                    ← ADDED
    }

  WHY?
    • Dockerfile installs ext-intl (line 29-30):
        docker-php-ext-install ... intl ...
    
    • But composer.json didn't declare it
    • Railway validates extensions: if declared in docker, must be in composer
    • Missing ext-intl = deployment failure
    • Now aligned with reality

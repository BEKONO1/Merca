                         HOW IT WORKS


    STEP 1: Reads files
    ─────────────────
    application/migrations/*.sql
    │
    ├─ 001_example_schema.sql
    ├─ 002_create_users.sql
    └─ 003_add_products.sql

    STEP 2: Checks tracking table
    ─────────────────────────────
    migrations table
    │
    ├─ id  │ migration                │ executed_at
    ├─ 1   │ 001_example_schema.sql   │ 2024-02-15 14:30:25
    └─ 2   │ 002_create_users.sql     │ 2024-02-15 14:30:26

    STEP 3: Executes missing migrations
    ──────────────────────────────────
    Runs only 003_add_products.sql
    (skips 001 and 002 - already done)

    STEP 4: Logs execution
    ──────────────────────
    ✅ Migrated: 003_add_products.sql (5 statements)
    ✅ Migration completed successfully

                    MIGRATION FILE NAMING


    Recommended patterns (files execute alphabetically):

    Numeric:      001_init.sql, 002_users.sql, 003_orders.sql
    Timestamp:    202402151430_init.sql, 202402151431_users.sql
    Date-based:   2024-02-15_init.sql, 2024-02-16_users.sql

    ⚠️  Don't rename files after first run!
       The tracking table remembers by filename.

                      TROUBLESHOOTING


    Error: "Migrations directory not found"
    → mkdir -p application/migrations

    Error: "No SQL migration files found"
    → Add *.sql files to application/migrations/

    Error: "Connection Error"
    → Check DATABASE_URL (Railway) or .env (local)
    → Check MySQL server is running

    Error: "SQL syntax error"
    → Check .sql file content
    → Test SQL in MySQL client first
